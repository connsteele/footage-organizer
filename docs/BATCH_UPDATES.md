# Held-clip follow-up reviews

Use **Export held clips for review** in the current batch. The app saves a review request with the exact held clips, current paths, proposed placements, user notes, batch decisions, and original evidence. Its Markdown kit is reference material for the agent, not an import file. It includes the request ID, project and batch IDs, the update schema, and a tailored response example. Footage must be supplied separately when the agent cannot access the local folders.

The original evidence includes handoff markers and their saved decisions, plus `localMarkers` for user additions and chapters first edited in Preview. Chapters merely viewed in Preview are not added to the export. Review markers and surrounding footage first, then use those events to refine the clip name/destination. Include optional `markerProposals: {schemaVersion: 1, items: [...]}` using the same markerId, originalLabel, seconds, proposedLabel and rationale contract as the normal handoff. Local markers can receive rename proposals using their exact ID, label and time. Preserve originals; do not invent chapter bindings. Never propose a rename for a marker whose decision is `deleted`; the user must restore it and export a fresh request first. Recommend additions/deletions in the rationale for the user to perform in the app. Changes to local markers since export cause a conflict, just like changed decisions.

Consider the original clip filename alongside the current proposal, markers, footage, user notes, and naming preferences. Retain useful identifiers and context unless the evidence or user instructions justify a correction. Explain meaningful changes; marker review does not replace filename context, and a suitable name can stay unchanged.

The request also includes the whole clip's `reviewed` flag (absent means false). Respect it as user progress, separately from marker decisions or filing. A changed flag after export causes a conflict. Applying returned suggestions resets the affected clip to Needs review while keeping it held; the user verifies the new suggestions. Do not include a reviewed flag in your returned update.

Review only the supplied held clips. Respect the user's notes and explain changed suggestions. Return a UTF-8 JSON object following `batch-update.schema.json`, with `kind: "batch-update"` and `schemaVersion: 1`. Copy `requestId`, `projectId`, and `batchId` from the request. Choose a new `updateId` and actual ISO timestamp for each distinct response. IDs use letters, digits, hyphens, and underscores, at most 80 characters. Include each reviewed clip once; a subset is allowed. Each entry contains its existing `id`, `proposed` filename/folder, `rationale`, and `questions` (an empty array when resolved), plus optional `markerProposals`. Use root-relative destination folders and preserve file extensions. Do not include new clips, source-path edits, hold flags, user notes, or other fields. Do not move footage or modify app state.

The user chooses **Import batch update** in that same batch. The app previews the current and suggested placements, explanations, and unanswered questions. It checks the stored request, source identity/location, filed/held status, user notes, placements, and batch decisions. Changes made since export are flagged; conflicted suggestions cannot be selected. The user can apply the unaffected suggestions and export a fresh request for the others. A batch revision check prevents changes made after preview from being silently replaced.

Applying selected suggestions updates that batch's proposed names/folders and adds a follow-up explanation. It preserves user notes, original import suggestions, and the before/after history. All updated clips stay held and need whole-clip review again. The user reviews them, releases the hold, marks the clip Reviewed, and confirms Move clips from the queue. Applying an update does not move files. Marker suggestions enter the batch as pending individual decisions: review them in Details before accepting. Unmentioned marker decisions are preserved. Changed marker decisions since export cause a conflict, just like changed clip placements. Already accepted suggestions are marked and cannot be applied twice. Remaining suggestions from the same unchanged update may be applied later; a changed payload needs a new update ID.

Filed clips cannot be changed through this workflow. A source that changed on disk needs a fresh handoff and review baseline. This workflow is separate from importing a new batch: use the normal handoff format for new footage.

The runtime schema is `reviewUpdateSchema` in `src/shared/model.ts`. Regenerate the published schema with `npm run schema`. Request snapshots and accepted update history are stored with the batch in its plan folder; plan JSON, Markdown, and later context kits preserve the decisions.
