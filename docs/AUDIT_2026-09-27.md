# Code and workflow audit — September 27, 2026

Reviewed the app at commit `3ae91b5`, then fixed the issues below. All media operations used disposable projects. No existing project state, source footage, desktop shortcuts, or running user server were changed during testing.

## Findings and fixes

| Area | Trigger and previous behavior | Fixed behavior |
| --- | --- | --- |
| User notes and holds | Reset suggestion cleared a user's note and restored the imported hold status. A user-held clip could become eligible for filing. | Reset only changes the proposed name and folder; notes and holds are preserved. A component test exercises the button and autosave. |
| Windows record collisions | Importing a batch or handoff ID differing only in capitalization could overwrite existing JSON/Markdown records. | Reject capitalization collisions before writing; exact reimports still preserve saved edits. |
| Reserved record IDs | IDs such as CON or NUL passed the handoff schema even though they become invalid Windows filenames. | Reject device names in the importer, CLI validator, and generated handoff schema. |
| Placement validation | The importer accepted a changed extension, leaving the error until move review. A manually edited filename containing a directory separator could be interpreted as a nested destination. | Reject extension changes on import and separators in filenames during preflight. |
| Project storage | Some combinations allowed a footage folder inside another project's plan folder, or plans inside the app registry folder. | Check both directions of folder containment and keep project storage separate from app storage. |
| External playback | After another batch moved a clip, an older batch's external-player action looked at its historical path. MXF/MTS/M2TS could appear in inventory but be rejected by the external-player action. | Resolve and verify the current catalog path; accept the same media extensions as inventory and preview. Actual codec support remains player-dependent. |
| Cleanup retry | If files were deleted but removal-registry persistence failed, a retry required the now-deleted state.json and could never finish. | Save a verified cleanup manifest first. Retry handles missing records and preserves records whose identity changed after cleanup began. |
| Move persistence failure | A failed journal save could leave a stopped job recorded as running. The browser kept polling indefinitely, and another review did not flag that unresolved journal. | Block further moves pending recovery; project polling reconciles the orphan journal when storage becomes available. It identifies completed moves without repeating them. |
| Shared clips and operations | Ambiguity checks only applied to the original batch, and repeating an operation ID through another batch's endpoint returned that unrelated operation. | Block ambiguous shared clips across batches and reject an operation/batch mismatch. |
| Shutdown race | Shutdown could be acknowledged while a save was queued and still admitted new mutations before process exit. | Serialize shutdown with saves, refuse active moves, and stop admitting mutations before acknowledgement. Process shutdown drains outstanding work. |
| Error handling | A recovered project-list request left its old error banner visible. Oversized JSON returned a server error. | Clear the banner after a successful refresh and return a readable 413 response for requests over 8 MB. |
| Test dependencies | npm audit reported a moderate advisory through Vitest and its mocking package. | Update the development dependency to Vitest 4.1.11, the patched version identified by the [maintainer advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9), and refresh the lockfile. This package is test tooling, not part of the built app. |

The initial targeted tests reproduced nine failures before their fixes. A separate UI test reproduced note loss when resetting a suggestion. Other tests extend coverage of the related boundary cases, especially shutdown, ambiguous shared clips, and replaced cleanup records.

They cover UI navigation, exports, failed saves, selective update conflicts, deletion cancellation and both choices, unrelated-file preservation, actual H.264 playback and scrubbing, and playback after a move.

Automated tests are kept in `tests/`. Browser screenshots and disposable fixtures are in the task's configured scratch storage, outside the repository. No personal handoffs or real project data are included in these tests.

## Testing limits

This audit does not establish that every codec, drive, network share, or power-loss scenario works. Fault injection simulated failed writes; the machine and storage device were not physically interrupted. Actual external-player decoding and native Windows folder selection remain unverified visually. The in-app browser connector still failed its trusted-path setup, so browser checks used a fresh isolated Edge profile. Original-media playback remains dependent on browser/OS codecs. Cross-volume moves remain intentionally unsupported.

## Recommended next steps

1. **A project-wide held-review inbox.** Show unresolved clips from all batches with the user's latest note, latest agent response, source batch, and a direct return link. Keep acceptance within each existing batch. This addresses the two or three clips left behind while new footage batches continue.
2. **Clickable markers and timecoded notes.** Jump from an imported marker to the in-app player and attach the current playback time to a held note. Include that time in the agent-follow-up kit so the next conversation can inspect the precise moment.
3. **Remember the review position.** Restore the selected view, search, open clip, and scroll position when returning to a batch. Keep Remaining as the default for a newly opened batch. Add explicit next/previous clip controls before more elaborate keyboard shortcuts.
4. **A restore action for retained projects and deliberate plan backups.** Reopening currently requires entering the same ID and folders. A Restore action in the removed-project list would make the reversible option clear. A portable plan backup would complement the rolling checkpoints before permanent cleanup or relocating a project.
5. **Measure larger real projects before changing storage or the stack.** The app currently loads whole project state and rewrites readable snapshots on saves. Profile accumulated batches and follow-up history before considering incremental storage or row virtualization. The 250-clip check did not expose an immediate need for either.

These are proposals, not additional features included in the audit fixes. The existing React/TypeScript/CSS Modules stack still fits this local review workflow; the failures found here concerned validation, state transitions, and recovery rather than a language limitation.
