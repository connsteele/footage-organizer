## Observed performance

These are local fixture observations, not performance guarantees. The 1,500-marker comparison used the same generated 12-second clip, 1,920 × 1,080 viewport, and a four-second playback sampling window. The playback metric is browser main-thread task time, not decoder/GPU usage. Heap observations include browser allocation and garbage-collection variability.

| 1,500-marker scenario                        |   Before |  After |
| -------------------------------------------- | -------: | -----: |
| Open preview and marker fields               | 1,096 ms | 808 ms |
| Main-thread task time during playback sample | 1,242 ms | 268 ms |
| Observed JavaScript heap                     |    86 MB |  49 MB |
| Replace a marker name                        |   225 ms | 134 ms |

In the 1,000-clip run, opening the batch took about 502 ms and filtering to one clip about 215 ms. At 10,000 markers, opening took roughly 5–6 seconds and an edit roughly 0.9 seconds. That limit remained functional, but rendering every card is still expensive. Runs overlapped other checks, so extreme-case times are approximate rather than a controlled before/after comparison.

## Recommended next steps

1. **Render only visible marker cards for very large lists.** Use a variable-height list that retains focus, scrolling position, open reasoning, and editable decisions. This addresses the remaining measured extreme-case bottleneck. Apply the same idea to clip rows only if normal batch sizes warrant it.
2. **Make review completion explicit for unchanged clips.** Such clips currently stay in Remaining because no file operation has filed them. A separate reviewed/completed state would let a user finish review without inventing a file move. Keep that state distinct from the operation journal.
3. **Add next/previous clip controls and restore playback position.** These fit a repeated review workflow and reduce reopening, scrolling, and re-seeking. A project-level held-clips view would similarly make unresolved work easier to resume across batches.
4. **Measure project-history growth before changing persistence.** Many batches and repeated follow-up snapshots can make full-state parsing, checkpoints, and materialized exports costly. Consider targeted export writes and a per-batch storage boundary, with interruption/recovery tests written before changing durability ordering.
5. **Further component/CSS separation as those areas change.** Move-confirmation/progress components and feature-specific CSS are useful next boundaries. Avoid turning the understandable local app into a generalized framework solely to reduce individual file lengths.

The current practice tour remains useful for hands-on testing, including its existing 27-marker scrolling lesson. This pass changes implementation and fixes behavior; it does not replace existing practice decisions or add thousands of markers to the user's everyday demo.
